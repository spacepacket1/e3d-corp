## Implementation Handoff

- `lib/outcomes/schema.js`: `OUTCOME_TYPES`, the documented starter list. **One deliberate deviation from the spec's literal text**: the spec names an Outcome type `proposal.rejected` (an external party rejecting our proposal/quote), which is a literal event-`type` collision with Phase 5's Decision event type of the same name (e3d-corp/a human rejecting a Proposal object internally) - two different real-world facts that would become indistinguishable under `queryEvents({type: 'proposal.rejected'})`, directly undermining the spec's own "Decision vs Outcome are separate objects, evaluation metrics must not conflate them" requirement (Product Goals). Renamed to `outcome.proposal.rejected`; every other listed type (including `proposal.accepted`, which does *not* collide with Phase 5's `proposal.approved`) keeps its literal spec name. `capability.shipped` is reused exactly as Phase 8 already emits it - not double-defined.
- `lib/outcomes/record.js`: `recordOutcome(dataDir, { correlationId, type, payload, occurredAt })` - the single implementation both the CLI and web form call. Requires the correlationId to already have real events (refuses to record an outcome for a chain that doesn't exist) and a known `type`. Appends the outcome as a raw event (its `type` field *is* the outcome type, matching Decisions' own pattern - `source: 'outcomes.record'`). Deliberately **not** gated behind Phase 5's authority/Decision framework: recording a fact isn't an action e3d-corp performs on the world, so there's nothing to approve - only something to note down accurately (this *is* the spec's "human records what actually happened" line). Every successful call also assembles and appends a fresh Experience snapshot (below) - the natural point at which a chain becomes "meaningfully completed."
- `lib/outcomes/store.js`: `listOutcomes(dataDir)` folds all `OUTCOME_TYPES` events from the log, same pattern Opportunities/Proposals/Actions already use.
- `lib/experience/assemble.js`: `assembleExperience(dataDir, correlationId)` - a pure fold over `reconstructChain`, producing `{ correlationId, context, originatingEvent, evidence, role, model, proposal, decision, action, outcome, latencyMs, costEstimate }`. `role`/`model` come only from what the log actually recorded (a proposal's `proposedBy` if one exists in the chain, else the opportunity's `role:<name>` source with `model: null` - never fabricated). `action` reuses Phase 7/8's own `ACTION_FIRED_EVENT_TYPES` list (now exported from `lib/actions/log.js` instead of duplicated). **`costEstimate` is always `null`**: no LLM call anywhere in this codebase currently records token usage or cost, so there is nothing real to report - a future phase needs to add that instrumentation before this field can be honestly populated. Every field is always present (even when `null`), satisfying "no missing required field" without fabricating data.
- `lib/experience/store.js`: `<dataDir>/experience.jsonl`, append-only (mirrors `events.jsonl`'s own discipline - never rewritten), `readExperience`/`listExperience` fold "latest wins" per `correlationId`, same pattern as everything else in this codebase.
- `lib/cli.js`: `outcomes record --correlation <id> --type <type> --payload <json> [--occurred-at <iso>]` and `experience show <correlationId>` (both were Phase 1-6 stubs, now real).
- `lib/web/server.js` + `render.js`: `/opportunities/:id` gained an outcome-recording form (type select + JSON payload textarea -> `POST .../outcomes`) and a link to `GET .../experience` (read-only, no CSRF, always a live recompute - not a read of the persisted snapshot, so it reflects the chain's current state even before any Outcome has been recorded). New top-level `GET /outcomes` list view, nav link added.
- Tests: `test/phase9.test.js` (7 new tests) - `OUTCOME_TYPES` collision-avoidance, `recordOutcome`'s real-chain/known-type requirements and its experience-snapshot side effect, `listOutcomes`, `assembleExperience` against both a full fixture chain (every field populated, matches the phase's literal acceptance criterion) and a bare chain (every field still present, correctly `null`), and the phase's other literal acceptance criterion: recording an outcome against a real Phase-7-shaped chain via the CLI *and* the web UI for the *same* correlationId, confirming both surfaces' events show up identically in `reconstructChain` and in `/outcomes`/`/opportunities/:id/experience`.
