# Feature Ticket: Generic Spreadsheet-Backed Capital Intelligence Event Source

## Overview

FutCo's operator maintains an external household/capital-portfolio spreadsheet as a running source of financial evidence — net worth, recovery-zone status, crypto-linked concentration risk, and FutCo's own funding gap against household capital policy. Today `e3d-corp` has no way to see any of it; every Opportunity it drafts is blind to capital reality. This ticket gives `e3d-corp` a **read-only** way to ingest that evidence, exactly like `lib/event-sources/googleCalendarBooking.js` already turns a Google Calendar booking into a `lead.received` event that flows through the existing Opportunity engine — same shape, different evidence source.

**This is an evidence source, not a financial actor.** The adapter reads a spreadsheet, normalizes it, diffs it against the last known state, and appends Company Events. Nothing it does can place a trade, move money, or touch an exchange/brokerage — see Non-Goals and the Authority Boundary shared constraint below, which is the part of this ticket that must survive review unchanged.

**Hard genericity constraint, added during review, binding on every phase:** no code, config schema, example file, or doc committed to this repo may name the operator's actual spreadsheet, its tab names, its spreadsheet ID, or any of its metric key strings. The adapter is a generic "read a contract-shaped Google Sheet, turn it into evidence" tool. Every operator-specific identifier — spreadsheet ID, sheet/tab name(s), service-account key file — lives only in `.e3d-corp/instance/<name>/` (already fully gitignored — confirmed via `.gitignore`) or in environment variables. Tracked files use placeholder values only (see `examples/instance.example.json`'s existing pattern: `EXAMPLECO_*` env var names, no real secrets). This is stricter than the pre-existing "don't put credential *values* in git" convention — it also means don't put the spreadsheet's *structural specifics* in git, because the operator does not want this instance's capital-tracking spreadsheet identifiable from the public repo at all.

The one thing that makes this tractable without the adapter knowing anything BloomPortfolio-specific: the contract sheet's own **`Event Type` column** declares, per row, which `e3d-corp` event type a change to that row should produce. The adapter never hardcodes a metric-to-event-type mapping — it reads whatever the sheet declares. This is what makes "generic, contract-driven, no hardcoded specifics" actually work, not just a constraint layered on top.

## Product Goals

- A generic, reusable Google Sheets read adapter (`lib/sheets/`) that any instance can point at any spreadsheet+tab via config — no code changes required to onboard a new sheet, only config.
- A contract-driven normalizer that reads a configured tab by **header name** (`Key`, `Value`, `Unit`, `Type`, `Sensitivity`, `Consumer`, `Event Type`, `Authority`, `Freshness`, `Description` — order-independent, tolerant of column reordering/insertion), producing a normalized snapshot: `{ observedAt, source: { type: "google-sheet", spreadsheetId, sheet }, metrics: { "<key from sheet>": { value, unit, type, sensitivity, eventType, authorityHint, freshness, description } } }`.
- Deterministic, event-sourced change detection: every successful read appends `portfolio.snapshot`; a **discrete state change** in a `Type: status`-flavored row (fold the prior classification state from event history, not from a side file) appends the row's declared `Event Type` — but only when the state actually differs from the last known state for that key, never on every poll.
- A source-health state machine: `portfolio.data.degraded` on a read/parse failure (fail closed — never invent a value), `portfolio.data.restored` on the next successful read after a degraded period. Both derived by folding prior `portfolio.data.*` events, not a side flag.
- Portfolio change events feed the **existing** `runOpportunityEngine`/`opportunity.prospect` pipeline as their `triggerEvent`, exactly like `ops/reports/pollCalendarBookings.js` already does for calendar bookings — no second opportunity engine, no bypass of the existing scoring/evidence machinery.
- A cron-polled ingestion script (`ops/reports/pollPortfolioSheet.js` + `ops/run/run-portfolio-poll.sh`), matching the calendar-poll pattern exactly, plus a manual CLI command (`e3d-corp portfolio status --instance <name>`) for on-demand testing.
- Preserve every convention this codebase has already earned: config holds env var names/generic field names, never secret values or operator-specific identifiers; nothing fails open on a parse/auth error; the authority system is not touched, weakened, or given a new bypass path.

## Non-Goals

- **No action executor of any kind for trading, transfers, brokerage/exchange connectivity, or asset movement.** Not a stub, not a disabled flag, not a "future executor" placeholder — this ticket adds zero lines of code capable of moving money or placing an order. If a future ticket ever proposes one, it starts its own review from zero, not as an extension of this adapter.
- Do not add a new action `type` to `lib/authority/policy.js`'s `ACTION_POLICY` table in this ticket. Nothing this ticket builds executes a Proposal — it only creates Events and (via the existing engine) Opportunities, both authority level ≤ 1, autonomous, no Decision required (`lib/authority/policy.js`'s own comment: levels 0–1 never generate a Proposal/Decision).
- Do not read `Capital_Policy`- or `FutCo_Capital`-style tabs directly, and do not name any such tab in code. Decision made in this ticket (see Shared Constraints, "Single contract tab, not sheet-formula coupling"): if the operator's spreadsheet computes policy thresholds or FutCo-funding-gap state on other tabs, that computation's *output* must already be surfaced as ordinary rows on the one configured contract tab for this adapter to see it. This keeps the adapter decoupled from arbitrary spreadsheet formulas and genuinely generic — it has no tab-name-shaped knowledge of any particular spreadsheet's internal structure beyond "the one tab named in config."
- Do not use an LLM to decide whether a numeric or status value changed, or to compute any threshold/materiality judgment. All change detection is deterministic string/value comparison against folded event history.
- Do not build household-capital commitment logic, funding-gap arithmetic, or any capital-allocation decision-making in this ticket. A `futco.capital.gap` event is emitted **only** when the contract sheet itself declares a row with that `Event Type` and that row's value changes state — the adapter does no independent gap computation and assumes zero commitment unless the sheet's own declared value says otherwise (Shared Constraints, "No forced-sale reasoning").
- Do not build a second, portfolio-specific opportunity-scoring or research pipeline. Reuse `runOpportunityEngine` as-is.
- Do not change `web/` to display raw portfolio values in this ticket — out of scope; CLI + event log are the only surfaces.

## Shared Constraints

### The authority boundary (non-negotiable, applies to every phase)

- Every event and Opportunity this adapter or its downstream `opportunity.prospect` call produces is authority level 0 (observation: the snapshot/change events themselves) or level 1 (internal write: an Opportunity or draft Proposal *for review*, same as any other Opportunity in this system today). Nothing produced by this ticket's code reaches level 2 (external action), 3 (financial action), or 4 (irreversible action).
- If a future human decision on a portfolio-derived Opportunity leads to an actual proposed financial action, that Proposal is drafted and gated through the **existing, unmodified** Proposal → Decision → `confirmAndExecute` flow, at whatever authority level a *real, separately-reviewed* action type earns in `ACTION_POLICY` — which, per Non-Goals, this ticket does not define, because it defines no financial action type at all. There is deliberately no code path from "portfolio event" to "money moves" shorter than "human writes and approves a brand-new action type in a future ticket."
- Do not read `Authority` off the contract sheet and use it to set or short-circuit an Opportunity's or Proposal's actual `authorityLevel`. Capture it as `authorityHint` — passthrough metadata for a human or the `opportunity.prospect` LLM role to reason about in the *content* of a recommendation — never as a value that changes what the code itself is permitted to do. The code's authority ceiling is fixed by this ticket's own scope (0/1 only), not by spreadsheet content.

### Single contract tab, not sheet-formula coupling

The adapter reads exactly one configured tab (`portfolio.sheetName` in config) from exactly one configured spreadsheet (`portfolio.spreadsheetId`). It has no knowledge of, and never reads, any other tab. If the operator's spreadsheet has other tabs computing policy thresholds or funding-gap arithmetic, those tabs must publish their computed *output* as ordinary rows on the one configured contract tab (by formula, on the spreadsheet side — not this codebase's concern) for the adapter to see them. This is the smallest integration consistent with existing architecture (no new sheet-formula parser, no second read path) and is what keeps the code genuinely generic rather than shaped around one operator's specific multi-tab layout.

### Contract shape (read by header name, not position)

The configured tab's first row is headers. Recognized headers (case-sensitive match against exact strings, tolerant of column order): `Key`, `Value`, `Unit`, `Type`, `Sensitivity`, `Consumer`, `Event Type`, `Authority`, `Freshness`, `Description`. `Key` and `Value` are required on every data row; a row missing `Key` is skipped (logged, not fatal — a spreadsheet mid-edit shouldn't take the whole read down). A tab missing the `Key` or `Value` header entirely is a hard parse failure → `portfolio.data.degraded`, not a partial read. `Type` recognized values: `number`, `percentage`, `string`, `status` (case-insensitive) — an unrecognized `Type` value is treated as `string` (value read as-is, no coercion), not a failure.

### Deterministic classification rule

- A row with a non-empty `Event Type` is a **classified** row. Its prior state is the last value `e3d-corp` observed for that exact `Key` (folded from the most recent event of that declared type carrying that key in its payload — not from every `portfolio.snapshot`, to keep the fold cheap and bounded). If the current read's value for that key differs (string/value inequality — for `Type: number`/`percentage`, exact value comparison; the spreadsheet, not this code, is responsible for pre-rounding/pre-classifying if it wants coarser-grained change detection, per "Single contract tab" above) from the folded prior state, append one event of the row's declared `Event Type`, payload carrying `{ key, previousValue, value, unit, type, freshness }`. If unchanged, no event — this is what keeps ordinary unclassified drift and repeat identical reads silent (Acceptance Criteria, Phase 2).
- A row with an empty/missing `Event Type` contributes to `portfolio.snapshot`'s `metrics` map only — never generates its own event.
- `portfolio.snapshot` itself is appended on **every** successful read, unconditionally (it's the raw evidence timestamp, analogous to `e3d-trade`'s own `portfolioSnapshotWriter.js` pattern of an unconditional periodic snapshot) — the "no noisy duplicates" requirement (Acceptance Criteria) applies to the *classified* change events, not to the snapshot's own cadence. If this later proves too noisy for the event log, thinning `portfolio.snapshot` frequency is a follow-up config knob, not this ticket's concern.

### No forced-sale reasoning; capital events are read-through, not computed

`futco.capital.gap` (and any other capital-flavored `Event Type` the sheet declares) is emitted exactly like any other classified row: the code reads whatever value/state the sheet already computed and reports a change. The code does not compute a funding gap, does not know what "Max Household Funding Commitment" means, and never treats "zero" specially versus any other value — the sheet's own zero-means-zero semantics (per the operator's original framing) live entirely in the spreadsheet, never re-derived here. This is what "read-only evidence source, not a financial actor" means concretely at the code level: there is no arithmetic in this adapter that could be described as a funding or allocation decision.

### Privacy / logging

- No log line (CLI stdout, cron log file, error message) ever includes the raw `Value` of a row whose `Sensitivity` is anything other than absent/`low` — logs reference the `Key` and status (e.g., `"metric X changed"`) by default. `portfolio status`'s default CLI output follows the same rule; add a `--reveal` flag to opt into printing actual values for a specific manual debugging session (never the default). This is defense-in-depth on top of (not a substitute for) `.e3d-corp/instance/` already being fully gitignored.
- Never log service-account credential contents (the existing `loadServiceAccountCredentials` already doesn't; keep it that way through the extraction in Phase 1).

## Phase 1 — Generic Google Sheets Read Client; Extract Shared Service-Account Auth

### Requirements

- Extract `loadServiceAccountCredentials`/`getServiceAccountAccessToken` from `lib/calendar/googleServiceAccount.js` into a shared, non-calendar-namespaced location — `lib/google/serviceAccount.js`. Update `lib/calendar/googleServiceAccount.js`'s one real caller (`ops/reports/pollCalendarBookings.js`) to import from the new location; delete the old file rather than leaving a re-export shim (it has exactly one caller today, confirmed by repo-wide grep — a shim would be dead weight, not a compatibility need). `CALENDAR_READONLY_SCOPE` stays exported from wherever the calendar code still needs it (or moves inline to `lib/calendar/googleCalendarApi.js`'s caller) — the shared module exports no scope constant of its own, since scope is caller-supplied per use (Sheets and Calendar need different scopes).
- Add `lib/sheets/googleSheetsReadonly.js`: `getSheetValues({ accessToken, spreadsheetId, range })` — a thin `fetch` wrapper over Sheets API v4 `GET /v4/spreadsheets/{spreadsheetId}/values/{range}`, returning the parsed `{ range, majorDimension, values: string[][] }` response, matching `lib/calendar/googleCalendarApi.js`'s error-handling shape (non-2xx → throw with status + response text, no swallowed errors). No `googleapis` npm dependency, matching the existing convention.
- `SHEETS_READONLY_SCOPE = 'https://www.googleapis.com/auth/spreadsheets.readonly'` exported alongside `getSheetValues`.

### Acceptance Criteria

- `getServiceAccountAccessToken` called with `scope: SHEETS_READONLY_SCOPE` against a mocked token endpoint returns a token exactly as it does today for the calendar scope — same function, different scope argument, verified via a test double (no live Google call in tests).
- `getSheetValues` against a mocked HTTP response returns the parsed `values` 2D array; against a mocked 4xx/5xx response, throws with the status code and body text in the error message (mirroring `listUpcomingCalendarEvents`'s existing error format).
- The old `lib/calendar/googleServiceAccount.js` path no longer exists; `pollCalendarBookings.js` and any other caller import from `lib/google/serviceAccount.js` instead; existing calendar-poll tests still pass unmodified in behavior (only the import path changes).
- No test, fixture, or mock in this phase references a real spreadsheet ID, tab name, or credential value.

## Phase 2 — Contract-Driven Snapshot Parser, Normalizer, and Event-Sourced Diff/Classification

### Requirements

- Add `portfolio` to `.e3d-corp/config.schema.json` and `validateInstanceConfig` (`lib/config.js`), matching the `calendar` object's convention: `{ provider: string, spreadsheetId: string, sheetName: string, serviceAccountKeyFileEnvVar: string }`, all required if the `portfolio` key is present at all (optional section — an instance with no portfolio source configured is valid and simply never polls one, same as `calendar` is optional today). `examples/instance.example.json` gets a fully generic example block (`"spreadsheetId": "REPLACE_WITH_SPREADSHEET_ID"`, `"sheetName": "REPLACE_WITH_SHEET_NAME"`, `"serviceAccountKeyFileEnvVar": "EXAMPLECO_PORTFOLIO_SERVICE_ACCOUNT_KEY_FILE"`) — no real BloomPortfolio identifiers anywhere in this file, ever.
- Add `lib/event-sources/portfolioSheet.js`:
  - `parseContractRows(values)` — takes the raw `values: string[][]` from `getSheetValues` (first row = headers), returns `{ rows: Array<{ key, value, unit, type, sensitivity, consumer, eventType, authorityHint, freshness, description }>, errors: string[] }`. Missing `Key`/`Value` header → throws (hard parse failure, caught by the caller and turned into `portfolio.data.degraded`). A data row missing `Key` is skipped and recorded in `errors`, not thrown.
  - `buildSnapshot({ rows, observedAt, spreadsheetId, sheetName })` — the normalized shape from Product Goals (`{ observedAt, source, metrics }`), keyed by each row's `Key`.
  - `foldPortfolioState(dataDir)` — queries `queryEvents` (`lib/events/store.js`, matching how `alreadyRecordedGoogleEventIds` folds calendar state today) for the most recent classified event per `Key`, plus the current `portfolio.data.degraded`/`.restored` status, returning `{ lastValueByKey: Map, degraded: boolean }`.
  - `classifyChanges({ snapshot, priorState })` — pure function implementing the Deterministic Classification Rule (Shared Constraints); returns the list of classified events to append (each `{ type, payload }`), never appends anything itself (keeps this function trivially unit-testable without an event store).
  - `ingestPortfolioSnapshot(dataDir, instanceConfig)` — orchestrates: fetch (Phase 1 client) → parse → on failure, fold current degraded status and append `portfolio.data.degraded` **only if not already degraded** (no repeat degraded spam either) with a payload carrying the error message and zero fabricated metric values (fail closed — no `metrics` key on a degraded event); on success, append `portfolio.snapshot`, append `portfolio.data.restored` if the prior state was degraded, then append each classified change event from `classifyChanges`. Returns the list of newly appended events for the caller (poll script / CLI) to report.
- Every appended event uses the existing `appendEvent` helper (`lib/events/store.js`) — same hash-chain, same `causationId`/`correlationId` conventions as every other event in this system (a poll cycle's events share one `correlationId`, generated once per `ingestPortfolioSnapshot` call, same pattern as `recordBookingReceived`/`runOpportunityEngine` already use elsewhere).

### Acceptance Criteria

- A fixture 2D array with headers in a shuffled, non-canonical order still parses correctly (header-name lookup, not position) — proves the "survives row/column reordering" acceptance criterion at the unit level.
- A fixture missing the `Value` header throws from `parseContractRows`; the orchestrator turns that into exactly one `portfolio.data.degraded` event, no `portfolio.snapshot`, no fabricated metrics.
- Two consecutive identical fixture reads produce two `portfolio.snapshot` events (unconditional) but zero classified change events on the second read.
- A fixture where a `Type: status`/`Event Type: <X>` row's value changes between two reads produces exactly one event of type `<X>`, payload carrying `previousValue`/`value`; a fixture where only an unclassified (`Event Type` empty) row's value changes produces zero classified events, only the unconditional snapshot.
- A degraded-then-recovered sequence (fail, fail, succeed) produces exactly one `portfolio.data.degraded` (not two) and exactly one `portfolio.data.restored` on the recovering read.
- No fixture, test name, or code comment in this phase names a real spreadsheet ID or tab name — generic fixtures only (e.g. `Key: "example.metric"`, sheet name `"Test_Sheet"`).
- `config validate` accepts an instance config with a fully-populated generic `portfolio` block and rejects one missing any required sub-field, matching the existing `calendar` validation test pattern.

## Phase 3 — Opportunity Integration, CLI Command, Cron Poll Script, Config Wiring

### Requirements

- `ops/reports/pollPortfolioSheet.js` (new, mirrors `pollCalendarBookings.js` structure exactly): loads instance config, requires `config.portfolio` to be present (clear error if not configured for this instance — same pattern as the calendar poll's `if (!calendar)` check), calls `ingestPortfolioSnapshot`, and for every newly appended **classified** event (not the plain `portfolio.snapshot`) whose declared `Event Type` warrants one, calls `runOpportunityEngine({ instanceConfig, dataDir, triggerEvent: <that event>, researchAdapter })`, logging the resulting Opportunity id/title/score exactly like the calendar poll does. `portfolio.data.degraded`/`.restored` and plain `.snapshot` events do not, by themselves, trigger `opportunity.prospect` — only the operator-declared classified events do (a `reconciliation-review`-flavored Opportunity for a degraded state is instead the *content* of one such classified event, e.g. a sheet-declared `portfolio.data.degraded` row if the operator wants one surfaced as an Opportunity trigger; keeps the mapping fully sheet-declared rather than code special-casing "degraded always means an Opportunity").
- `ops/run/run-portfolio-poll.sh` (new, mirrors `run-calendar-poll.sh` exactly: sources the instance's `.env`, `cd`s to repo root, execs the poll script with `--instance futco`).
- **Deployment correction, flagged explicitly:** the running FutCo instance has no PM2 app for scheduled work — `ecosystem.config.cjs` runs only the persistent web UI (`e3d-corp-futco-web`). Every scheduled report/poll (`run-calendar-poll.sh`, `run-daily-digest.sh`, `run-anchor-publish.sh`) runs via `crontab`, not PM2. This ticket adds a new cron line (`*/15 * * * * /Users/mini/e3d-corp/ops/run/run-portfolio-poll.sh >> .../portfolio-poll.log 2>&1`, matching the calendar poll's existing 15-minute cadence exactly) — it does **not** touch `ecosystem.config.cjs` and does not require a PM2 restart. The deployment checklist's "restart PM2, verify healthy" step still applies as a general sanity check that this change didn't destabilize the unrelated web process, but the actual new schedule is a crontab edit, not a PM2 change.
- `e3d-corp portfolio status --instance <name>` (new CLI command, added to `lib/cli.js`'s `COMMANDS` table matching the `providers status`/`budget status` naming and help-text style): runs one on-demand `ingestPortfolioSnapshot` call and prints a redacted summary — per key: `Key`, `Type`, `Freshness`, and (only for `Sensitivity: low`/absent, else `[redacted]`) `Value`; a `--reveal` flag overrides redaction for that one invocation only (Shared Constraints, Privacy/logging). Also reports current source health (`ok`/`degraded since <event time>`).
- Document (in this file's own "Recognized Opportunity Classes" note, not in code) the example open-string Opportunity `type` values a `portfolio.*`-triggered `opportunity.prospect` run may plausibly produce, for the LLM role's own prompt context: `capital-lock-in-prep`, `risk-reduction-review`, `liquidity-review`, `concentration-review`, `reconciliation-review`, `futco-capital-plan`, `capital-allocation-review`. These are recommendation/research Opportunities exactly like every other Opportunity type today — no schema change (Existing Integrations to Read First already confirms `type` is open). If `opportunity.prospect`'s existing role prompt needs these examples added as context so the LLM knows this is a recognized problem space, that's a prompt-content change in `lib/roles/opportunityProspect.js`, reviewed like any other role-prompt edit — not a new code path.

### Acceptance Criteria

- A stubbed classified change event run through `pollPortfolioSheet.js` (Google API and `runOpportunityEngine` both mocked) produces exactly one Opportunity, attributed to the portfolio event's `correlationId`, with no send-outreach or any level-≥2 Proposal produced anywhere in the chain.
- `portfolio status --instance futco` run against a mocked source prints key names and freshness for every metric but never a `Sensitivity: high` row's raw value unless `--reveal` is passed.
- `config validate` continues to pass for every existing example/fixture instance config unmodified by this ticket (a `portfolio` block is optional; omitting it is still valid).
- `event verify --instance <name>` (hash-chain verification) passes over a chain that includes portfolio-sourced events — proves this ticket didn't introduce any event shape that breaks chain verification.
- Full existing suite (`test/phase1.test.js` … `test/phase10.test.js`) passes unmodified in behavior; new tests for this ticket are added into the topically-closest existing phase files (event-source parsing → `phase2.test.js`, alongside the existing `googleCalendarBooking` tests; opportunity-engine integration → `phase4.test.js`; CLI → `phase1.test.js`, matching where `providers status`/`budget status` CLI tests already live) rather than a new `phase11.test.js`, matching this repo's existing pattern of extending phase files by topic rather than by ticket.
- No test in this phase makes a live network call to Google; the Sheets client is mocked throughout, per the original requirement that tests must not require live spreadsheet access.
