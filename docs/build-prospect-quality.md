# Feature Ticket: Prospect Quality — Separate Real Opportunities From Market Noise

## Overview

The `opportunity.prospect` role and the deterministic scorer that follows it
(`lib/opportunities/scoring.js`) were built to turn research evidence into
ranked Opportunity records. They work exactly as designed — and that design
has a real gap, found by auditing the live FutCo instance: of 70 opportunities
generated by the scheduled discovery pass, the highest-scored ones (0.816–0.876)
were the operator's own marketing site showing up in its own search results,
a competitor's marketing page (Bain & Company), and an unrelated third-party
product that happened to share a name with one of FutCo's own products ("Cast
AI," a Kubernetes cost-optimization company, matched against a research topic
about FutCo's own `cast.e3d.ai`). Zero of the 70 opportunities had ever been
marked `pursuing`; zero proposals existed anywhere in the instance.

The root cause isn't vagueness — `lib/roles/opportunityProspect.js`'s prompt
already explicitly forbids generic restatements and rewards an honest
low-confidence "nothing here" over a manufactured opportunity. The gap is that
the prompt, the candidate schema, and the scoring formula all treat "a named,
specific finding" as sufficient, with no axis anywhere that asks "is there an
actual counterparty here — a company or person FutCo could actually contact —
or is this just topically-relevant content?" A confidently-written competitor
page and a real prospect currently score on exactly the same scale.

This ticket adds that missing axis as a small, deterministic addition to the
existing pipeline — not a rewrite. The scoring formula, the role's overall
responsibilities, and the Event → Opportunity → Proposal → Decision flow are
all unchanged.

## Product Goals

- A cheap, deterministic filter that excludes the operator's own web
  properties from ever being scored as an Opportunity, configured generically
  (a list of domains in instance config), not hardcoded to any operator's
  actual domains.
- An explicit `counterparty` field on every Opportunity candidate — a named
  company/person and a contact hint, or an honest `kind: "none"` — so the
  presence or absence of an actual pursuit target is visible as structured
  data instead of hidden inside a plausible-sounding title.
- A deterministic, code-computed `pursuable` flag derived from `counterparty`,
  stored on the Opportunity record, so market intelligence (still useful to
  keep) never has to be deleted or suppressed to stop it from crowding out
  real prospects in the default views. Concretely: **the default list view's
  sort changes from score-only to pursuable-first** (score remains the
  tiebreaker within each group) — labeling rows without changing the default
  order would not actually satisfy this goal, since noise would still sit
  above real prospects by score alone.
- CLI and web UI opportunity views that surface `pursuable` and `counterparty`
  prominently, so a human reviewing the list can tell in one glance which
  items have a real next action behind them.
- An explicit instruction in the role prompt against the specific failure mode
  found in the audit: conflating a similarly- or identically-named but
  unrelated entity with the operator's own product of that name.

## Non-Goals

- No change to the scoring formula's existing three axes (confidence,
  evidenceCount, recency) or their weights — `pursuable` is a separate,
  deterministic derived field, not a fourth weighted score component. Mixing
  it into the numeric score would just recreate the same "everything competes
  on one axis" problem this ticket exists to fix.
- No change to `researchTopics` phrasing or content. The audit also showed
  that some topics are phrased as open market scans rather than
  buying-signal-oriented queries, which independently contributes to noise —
  that's a content/judgment call for the operator, not an engineering change,
  and is out of scope here.
- No automatic disqualification beyond the operator's own domains. The role
  still makes the counterparty call; this ticket does not attempt to build a
  general-purpose "is this company real" classifier.
- No change to `opportunities decide` / `propose-handoff` / outreach
  mechanics. This ticket only affects how an Opportunity is created and
  scored, not what happens after a human reviews one.
- No new authority level or ACTION_POLICY entry. Creating/scoring an
  Opportunity, including the new `counterparty`/`pursuable` fields, remains
  authority level 0/1 — autonomous, no approval required — exactly as it is
  today.

## Implementation Sequencing

1. **Phase 1 — Self-exclusion filtering, `counterparty`, and `pursuable`.**
   The core fix: stop scoring the operator's own site as an opportunity, and
   make "is there a real counterparty" a first-class, visible field.
2. **Phase 2 — Surface it in the CLI and web UI.**
   Update `opportunities list`/`show` and the web UI's opportunity views to
   display `counterparty` and `pursuable`, and let the CLI list be filtered/
   sorted by `pursuable`.

## Shared Constraints

**Deterministic, not a second LLM call.** `pursuable` and the domain-exclusion
filter are plain code — a boolean derived from `counterparty.kind`, and an
exact-hostname-or-subdomain match against a configured list (see below for
the precise rule — never a bare substring match). Neither should ever involve
a model call. This mirrors the existing scoring module's own stated
philosophy and keeps the new fields as auditable and cheap as the rest of the
pipeline.

**`counterparty` is required output, not optional metadata.** The role must
always populate it — either a real name/kind/contactHint, or the explicit
`kind: "none"` — the same way it's already required to always give a
`confidence` and `rationale`. `normalizeOpportunityCandidate` should reject a
candidate that omits `counterparty` entirely, the same way it already rejects
one missing `confidence`.

**Self-exclusion is domain-based, generic, and precisely specified — no
substring matching.** The `ownDomains` config field holds a plain array of
bare hostnames (e.g. `"example.com"`), populated per-instance. A result item
is excluded only when its URL's hostname (scheme stripped, case-insensitive)
exactly equals an `ownDomains` entry or is a subdomain of one (`hostname ===
entry || hostname.endsWith('.' + entry)`). Never a bare substring match — an
entry like `"ai"` must not match `openai.com`. `ownDomains` omitted or an
empty array means the filter is a no-op — nothing is excluded. An evidence
result item with no `.url` at all (common for knowledge-base results) is
never excluded by this filter, only web-search-style items with a URL are
eligible. Nothing about the filter, the schema, the config validator, or the
prompt may hardcode any specific operator's actual domain name.

**Filter before truncation, not after.** `summarizeEvidenceEvent` currently
takes `result.results.slice(0, 5)` before mapping to a summary. The
self-exclusion filter must run on the *full* results array first, then the
existing top-5 slice applies to what's left — filtering after the slice would
let an own-domain hit occupying one of the first five positions silently
crowd out an unrelated, real result sitting at position six or later.

**Don't silently drop evidence — filter what reaches the prompt, not what's
stored.** The domain filter should exclude self-domain results from the
evidence summary the LLM sees (so it can't cite them), not delete or mutate
the underlying `evidence.gathered` event — the raw research record stays
intact for audit purposes; only what's presented to the role changes.

**`counterparty` field consistency is a hard validation rule, not a
convention.** `kind: "none"` requires `name` and `contactHint` both `null`.
`kind: "company"` or `kind: "person"` requires a non-empty `name` string;
`contactHint` may be a non-empty string or `null`. `normalizeOpportunityCandidate`
must reject any candidate that violates this — a `"none"` with a name attached,
or a `"company"` with a null name, are both invalid, not just discouraged.

**`pursuable`/`counterparty` live on the `opportunity.created` payload.**
Per `lib/opportunities/store.js` above, that's the only event
`assembleOpportunities` uses for anything beyond `score`/`status` — both
fields must be part of the `record` object built in `runOpportunityEngine`
*before* `appendEvent` writes `opportunity.created`. Both values are known at
that point (they depend only on the candidate, not the score), so this
requires no reordering of the existing created-then-scored sequence.

**Historical opportunities have neither field, permanently — every reader of
`pursuable`/`counterparty` must treat their absence as valid input, not an
error.** Missing `pursuable` behaves as `false` (non-pursuable) for sorting
and filtering; missing `counterparty` renders as an explicit "unknown," never
a crash or a thrown error.

**Existing candidates already in the event log are not migrated.** The 70
opportunities already in the live futco instance keep their existing shape
(no `counterparty`/`pursuable`). This ticket only changes how new candidates
are produced going forward — no backfill, no rewrite of historical events.

## Phase 1 — Self-Exclusion Filtering, `counterparty`, and `pursuable`

### Requirements

- Add `ownDomains` (array of strings, optional) to `.e3d-corp/config.schema.json`
  at the top level, alongside `researchTopics`, **and** a matching validation
  block in `lib/config.js`'s `validateInstanceConfig` (see the existing
  `researchTopics` block for the pattern) — the schema file alone does not
  validate a loaded instance. Add a generic placeholder entry to
  `examples/instance.example.json`.
- In `lib/roles/opportunityProspect.js`, filter each evidence event's full
  `result.results` array by hostname against `instanceConfig.ownDomains`
  (exact-or-subdomain match, per Shared Constraints above) *before* the
  existing `slice(0, 5)` truncation in `summarizeEvidenceEvent` — a
  self-domain hit is removed from what the role sees, not from the stored
  event, and never at the cost of truncating away real results.
- Extend the candidate JSON shape the role must return with
  `"counterparty": {"name": string|null, "kind": "company"|"person"|"none",
  "contactHint": string|null}`. Update `buildSystemPrompt` to require it:
  name a real, contactable counterparty when one exists in the evidence, or
  set `kind: "none"` and leave `name`/`contactHint` null — the same
  "honest nothing is better than manufactured something" instruction the
  prompt already gives for confidence.
- Add an explicit anti-collision instruction to the prompt: if the evidence
  describes an entity that merely shares a name with one of the operator's
  own products, that is not a valid counterparty for a partnership/
  distribution opportunity about that product — the role must recognize and
  say so (routing it to `kind: "none"`, or, if it's a genuinely distinct
  finding in its own right, giving it its own honest title that doesn't imply
  a relationship that isn't there).
- Extend `validateOpportunityCandidate`/`normalizeOpportunityCandidate` in
  `lib/opportunities/schema.js` to require and validate `counterparty`,
  enforcing the exact `kind`/`name`/`contactHint` consistency rule from
  Shared Constraints — not just "present," but internally valid. Note that
  `normalizeOpportunityCandidate` returns a fixed, whitelisted set of fields
  today; `counterparty` must be added to that returned object explicitly, or
  a normalized candidate will silently drop it even after validation passes.
- In `lib/opportunities/engine.js`'s `runOpportunityEngine`, compute
  `pursuable = candidate.counterparty.kind !== 'none'` deterministically and
  set both `counterparty` and `pursuable` on the `record` object *before* it
  is written into the `opportunity.created` event payload (see the
  `store.js` note in Shared Constraints for why this specific placement is
  required, not optional).
- Update the shared test-fixture helper(s) that construct a valid candidate
  for existing opportunity-engine tests (e.g. a `validCandidate()`-style
  helper in whichever phase file currently covers `runOpportunityEngine` /
  `opportunity.prospect`) to include a valid `counterparty`, since it becomes
  a required field — do this as part of Phase 1, not as an incidental side
  effect discovered later.

### Acceptance Criteria

- A fixture evidence set containing only the operator's own domain (per
  `ownDomains`) produces zero eligible results reaching the prompt — verified
  by inspecting the built prompt/user message in a test, not by asserting on
  LLM output.
- A fixture evidence set with a mix of own-domain and other results has only
  the own-domain items excluded; unrelated results are untouched.
- A fixture with more than 5 raw results where an own-domain hit occupies one
  of the first 5 positions still surfaces the real result that was originally
  in position 6 — proving the filter runs before the truncation, not after.
- A knowledge-base-style evidence item with no `.url` field is never
  excluded, regardless of `ownDomains`.
- `ownDomains` omitted, and separately `ownDomains: []`, both produce
  identical (unfiltered) behavior to no configuration at all.
- Domain matching is exact-hostname-or-subdomain: `https://www.example.com/x`
  and `example.com` both match an `ownDomains` entry of `"example.com"`; an
  entry like `"ai"` does not match an unrelated domain such as
  `openai.com`.
- `lib/config.js`'s `validateInstanceConfig` accepts a valid `ownDomains`
  array and rejects a non-array value, mirroring the existing test coverage
  for `researchTopics`.
- `normalizeOpportunityCandidate` rejects a candidate missing `counterparty`,
  with an invalid `kind`, with `kind: "none"` and a non-null `name`, or with
  `kind: "company"`/`"person"` and a null `name` — and returns `counterparty`
  intact on a valid candidate (not silently dropped by the whitelist).
- `runOpportunityEngine`, given a candidate with `counterparty.kind: "none"`,
  produces a stored record with `pursuable: false`; given a candidate with
  `kind: "company"` and a name, produces `pursuable: true`. Covered by a unit
  test against the engine using a stub `llmClient` (the existing test pattern
  for this module), not a live LLM call. Verify both fields are present when
  the record is read back through `lib/opportunities/store.js`'s
  `getOpportunity`/`listOpportunities`, not only in the raw `opportunity.created`
  event payload.
- No test fixture or prompt string contains a real operator domain — only
  generic placeholders (`example.com`, `ourco.test`, etc.), consistent with
  the rest of this repo's test conventions.
- Existing opportunity-engine/scoring tests pass, using the updated shared
  candidate fixture helper (which now includes a valid `counterparty`) —
  "unchanged" applies to the assertions those tests make about scoring
  behavior, not to the fixture data itself.

## Phase 2 — Surface Pursuable and Counterparty in the CLI and Web UI

### Requirements

- `lib/opportunities/store.js`'s `listOpportunities` sort comparator changes
  from score-only to pursuable-first, score as tiebreaker within each group.
  A record with no `pursuable` field at all (every one of the 70 already in
  the live futco instance) sorts as if `pursuable: false` — treat a missing
  field as falsy, never throw on it.
- `lib/cli.js`'s `opportunities list` output includes `pursuable` (rendered
  plainly, e.g. as a visible marker distinguishing pursuable rows from
  intelligence-only rows) and the counterparty name when present, reflecting
  the new pursuable-first default order. Add a hard filter to pursuable-only
  (a new flag, e.g. `--pursuable-only`) that excludes non-pursuable and
  missing-field records, without removing the existing `--status`/
  `--min-score` filters — the three compose together.
- `opportunities show` renders the full `counterparty` object, or an explicit
  "unknown (predates this field)" when absent, never a crash.
- `lib/web/render.js`'s `renderOpportunitiesList` and
  `renderOpportunityDetail` are updated to show the same information — a
  visible pursuable/intelligence distinction in the list (reflecting the same
  pursuable-first order from `listOpportunities`), and the full counterparty
  block (or the same "unknown" fallback) in the detail view. Match the
  existing table/definition-list rendering style already used for
  `score`/`rationale`.

### Acceptance Criteria

- `listOpportunities` on a fixture data directory containing a mix of
  pursuable, non-pursuable, and field-missing (pre-existing-shape) records
  returns pursuable records first, score descending within each group, and
  never throws on a record missing `pursuable` entirely.
- `opportunities list --pursuable-only --instance <name>` returns only
  records with `pursuable: true`, excluding both `pursuable: false` and
  field-missing records, verified against a fixture data directory with all
  three shapes present. `--pursuable-only` composes correctly with
  `--status` and `--min-score` used together.
- `opportunities show <id> --instance <name>` output includes the
  counterparty name/kind/contactHint for a fixture opportunity that has one,
  and the explicit "unknown (predates this field)" fallback for a
  field-missing fixture — never a crash either way.
- Web UI rendering (via the existing HTTP-level test pattern for
  `lib/web/render.js`'s output, whatever that already is in this repo — there
  is no standalone render-function unit test today) covers a pursuable row, a
  non-pursuable row, and a field-missing row, in both the list and detail
  views, none of which crash the request.
- Full existing test suite passes.
- New tests are added to the existing topically-closest phase test file(s),
  not a new `phase11.test.js` — confirm the right file(s) via
  `grep -l "runOpportunityEngine\|opportunity.prospect\|scoreOpportunity"
  test/*.test.js` (engine/CLI-level) and `grep -l "renderOpportunit"
  test/*.test.js` (web-level) before adding, since more than one existing
  phase file may already touch this area.
