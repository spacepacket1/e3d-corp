# Feature Ticket: Multi-Provider Roles (Grok and Beyond)

## Overview

Today every role in `e3d-corp` (`opportunity.prospect`, `opportunity.communicator`) calls exactly one LLM: `lib/llm/localClient.js`, a single hardcoded, unauthenticated, OpenAI-chat-completions-compatible client pointed at whatever `instanceConfig.llm.baseUrlEnvVar`/`modelEnvVar` name. `roles.<name>.provider` already exists in config, but what it does with that value differs by role today: `communicator.js`'s `resolveRoleIdentity` reads it purely for attribution (stamped onto a Proposal's `proposedBy`), while `opportunityProspect.js` doesn't read `instanceConfig.roles` at all — it calls `createLocalLlmClient(instanceConfig)` directly, with no role-level dispatch or attribution whatsoever. There is no way to point a role at a hosted model, and no way to run a role through more than one model at all.

This ticket adds a **named provider registry** (multiple LLM endpoints an instance can define, one of which can be Grok's OpenAI-compatible API, or any other compatible host) and makes `roles.<name>.provider` an actual dispatch key that can name **one provider or a list of providers** — the same shape e3d-pilot already uses for `providers.<stage>` (see `../e3d-pilot/docs/grok-build.md`: `"negotiate": ["devin", "codex"]`). When a role names a list, every provider in it runs independently; what happens to their outputs differs by role, and that difference is the core design decision this ticket makes explicit below.

This is additive to the existing single-provider path: an instance that keeps one provider per role sees no behavior change.

## Why a provider list means different things for different roles

e3d-pilot's providers are agentic CLI tools (`claude`, `codex`, `devin`) producing a full idea/build; a provider list there needs a real merge step (`combine_ideate_responses`) because the pipeline ultimately wants one selected idea to build. `e3d-corp`'s roles are single-shot structured-JSON completions, and the two roles differ in what "more than one output" means:

- **`opportunity.prospect`** produces a *candidate Opportunity*, and Opportunities are already designed to coexist and be independently scored (Phase 4 of `docs/build-e3d-corp.md`). A provider list here needs **no merge algorithm at all** — each provider's candidate becomes its own scored, human-reviewable Opportunity. More providers just means more independent perspectives surfacing for the human to weigh, which is more in the spirit of "AI suggests, code decides" than picking one upfront.
- **`opportunity.communicator`** produces *one outreach draft* for *one already-approved* opportunity, and exactly one `send-outreach` action may ever fire per opportunity. A provider list here **does** need a decision point — but per this codebase's existing rule that scoring/selection is deterministic code, never a second model judging model output (`docs/build-e3d-corp.md`'s Phase 4: *"asking a model to score its own output is how you get confident nonsense"*), that decision point is the human, choosing among sibling drafts in the existing proposal-review UI — not an auto-ranking step.

## Product Goals

- Let `roles.<name>.provider` name one provider or a list of providers, exactly like e3d-pilot's `providers.<stage>`.
- Ship Grok as the first real hosted provider, authenticated against the existing `grok` CLI subscription/OAuth session (`grok login --device-auth`) — the same entitlement e3d-pilot's `lib/providers/grok-build` already uses — not xAI's separate pay-per-call `XAI_API_KEY` billing. Separately, build a generic OpenAI-compatible HTTP client so a *future* hosted provider (one billed and authenticated by a portable API key, unlike Grok's subscription) doesn't need bespoke per-vendor code — Grok is no longer that client's example.
- Preserve this codebase's existing conventions: config holds env var *names*, never secret values (README's "Secrets are never in the config"); nothing fails open on a misconfiguration (`e3d-corp`'s existing "the failure mode is nothing happens, never it happened unsupervised").
- Keep the human Decision framework as the only place multiple candidates get resolved into one outcome — multi-provider fan-out produces more things to review, never more things that happen automatically.
- Make every Opportunity and Proposal produced under multi-provider fan-out carry exactly which provider and model produced it, so a human reviewing three candidates from three providers can tell them apart.
- One provider failing must not silently kill the others in a list — record the failure as its own event, keep going, and only fail the whole role invocation if every configured provider fails.
- A hung or slow hosted provider must not hang the whole run — every provider call has a bounded timeout, local or hosted.

## Non-Goals

- Do not build automatic cross-provider selection, scoring, or merging in this ticket. e3d-pilot's optional `candidate_scoring` (deterministic re-ranking via worker fan-out, see `../e3d-pilot/docs/grok-build.md`) is a real precedent for a *future* ticket, gated on evidence from real multi-provider usage that humans actually want auto-ranking rather than picking themselves — do not build it speculatively now, the same reasoning `docs/build-e3d-corp.md` already applies to deferring CRM/ledger/multi-model negotiation.
- Do not add coding-agent-CLI-style providers (Claude Code, Codex, Devin). e3d-corp's roles are single-shot structured-JSON chat completions, not agentic build tasks — this ticket is scoped to chat-completions-style LLM providers only, unlike e3d-pilot's CLI-wrapper providers.
- Do not keep a backwards-compatibility shim for the old flat `llm.baseUrlEnvVar`/`llm.modelEnvVar`/`roles.<name>.model` shape. Migrate it to `llm.providers.local` cleanly (Phase 1) and update the real instance config to match, matching how this repo has already handled every prior config-field rename — no dual-format support, no silent fallback. `validateInstanceConfig` must name the old fields specifically in its error when it finds them, not report a generic schema mismatch.
- Do not build real spend budgeting/capping in this ticket. Fan-out multiplies real paid-API cost (`researchTopics` × configured providers × cron cadence), and that's a real risk — but this ticket's job is to make sure the *data* to eventually budget on is captured (per-provider latency, model, success/failure — see Phase 2/3), not to build the budgeting mechanism itself. That's future work for Phase 10's evaluation layer, once real multi-provider usage produces something to budget against.
- Do not change what `opportunity.prospect`/`opportunity.communicator` are allowed to do, or introduce a new authority level. A candidate from a second provider is exactly as autonomous (level 0/1) as one from the first; an extra outreach draft is exactly as gated (level 2) as the first.
- Do not deduplicate near-identical candidates across providers. A human already handles ordinary near-duplicate Opportunities today via the existing review flow; cross-provider duplicates are not a new problem class this ticket needs to solve.

## Implementation Sequencing

1. Phase 1 — Named provider registry; hosted OpenAI-compatible client with auth, timeout, and availability check; Grok as the first hosted provider
2. Phase 2 — Multi-provider fan-out for `opportunity.prospect` (list semantics, no merge needed)
3. Phase 3 — Multi-provider fan-out for `opportunity.communicator`; human selection between sibling drafts; atomic duplicate-outreach guard

Each phase is independently shippable and independently useful: Phase 1 alone lets an instance switch its one role provider from local to Grok; Phase 2 alone gets prospecting fan-out; Phase 3 completes the pattern for outreach.

## Shared Constraints

### Provider config, not provider code, is what changes per instance

- `llm.providers` is a map from an instance-chosen provider name (`"local"`, `"grok"`, anything) to a `kind`-specific shape:
  - `"local"`: `{ kind: "local", modelEnvVar, baseUrlEnvVar, timeoutMs? }` — unauthenticated; `baseUrlEnvVar` is required, there is no built-in default, matching `resolveLlmSettings`'s actual current behavior of throwing when it's unset.
  - `"openai-compatible"`: `{ kind: "openai-compatible", modelEnvVar, baseUrlEnvVar, apiKeyEnvVar, timeoutMs? }` — fully generic hosted HTTP client, for a *future* provider billed by a portable API key. Not what Grok uses.
  - `"grok-cli"`: `{ kind: "grok-cli", binEnvVar?, modelEnvVar?, timeoutMs? }` — subprocess-based, authenticated by the operator's own `grok login --device-auth` OAuth session (the subscription entitlement), not an API key. `binEnvVar` optionally overrides the `grok` binary name/path (mirrors e3d-pilot's `GROK_BUILD_BIN`, a literal env var name — not a secret, so no indirection needed beyond that). `modelEnvVar` is optional; when unset, the CLI's own configured default model is used and `proposedBy.model` records the sentinel `"grok-cli-default"` rather than fabricating a model name this ticket can't actually observe from outside the CLI.
  - `timeoutMs` is optional on every kind, defaulting to 60000 for HTTP kinds and to e3d-pilot's own `GROK_BUILD_TIMEOUT` default (900000ms) for `"grok-cli"`, since a CLI invocation is a materially heavier call than a chat-completions request.
- As with every other secret in this codebase, `apiKeyEnvVar` (where it applies) names an environment variable; it is never a value in config, and is never logged or included in any event payload. `grok-cli` has no such field — its credential is an out-of-band OAuth session the CLI itself manages, not something instance config ever touches.
- `roles.<name>` becomes `{ provider: string | string[] }` — `model` is removed from role config entirely. The model a role used is now always the *resolved* model from whichever provider entry actually served the call (`llm.providers.<name>.modelEnvVar`), read at call time — not a static label copied into config. (Today's `roles.<name>.model` is frequently a literal unresolved placeholder like `"$LLM_MODEL"`, stamped as-is into `proposedBy.model` — this is a strict improvement, not a behavior this ticket needs to preserve.) An instance that wants role A on a cheaper local model and role B on a stronger one defines two separate `llm.providers` entries and points each role at the one it wants.
- Every name in `roles.<name>.provider` must exist in `llm.providers`, checked by `validateInstanceConfig` — an unknown provider name fails config validation with a clear error naming the missing entry, the same "fails closed, names the problem" pattern `research.knowledgeBaseMcpServerPath` and the CLI's `--instance` flag already follow. `validateInstanceConfig` only checks config *shape* (as it does today for `llm.baseUrlEnvVar`, which validates against `examples/instance.example.json` with no real env vars set) — it does not check that the named env vars currently hold values. That's a separate, explicit runtime concern (below).

### Provider availability is a first-class, checkable thing — not just a call-time throw

- `runDiscoveryPass` already swallows per-topic errors into `results.push({ topic, error })` so one bad research call doesn't kill a whole cron pass — which means a misconfigured provider (missing API key, bad base URL, `grok` CLI not installed or not logged in) would otherwise degrade silently under cron instead of loudly on the operator's screen. Phase 1 adds `e3d-corp providers status --instance <name>`: for every entry in `llm.providers`, report readiness without making a real completion call — for `"local"`/`"openai-compatible"`, whether the required env vars are currently set (never their values); for `"grok-cli"`, whether the `grok` binary is present on `PATH` (or the configured `binEnvVar` path), mirroring e3d-pilot's own `E3D_PILOT_CHECK=1` mode in `lib/providers/grok-build` exactly — a binary-presence check, not a deep login-state probe, matching that precedent's actual scope rather than over-building this.

### Human authority is unchanged

- Multi-provider fan-out changes how many candidates/drafts get created, never what authority level they need or whether a human decision gates them. `opportunity.created`/`opportunity.scored` stay level 1 (autonomous) regardless of how many providers ran; `send-outreach` stays level 2 (human-gated) regardless of how many sibling drafts exist.

### Traceability

- Every Opportunity and every Proposal created under a multi-provider role carries `proposedBy: { role, provider, model }` naming exactly which provider produced it — extending the field Proposal already has (Phase 5 of `docs/build-e3d-corp.md`) to Opportunity, which does not have it today.
- A provider that fails within a fan-out list is recorded as its own `role.provider.failed` event (`payload: { role, provider, reason }`, `causationId` pointing at the triggering event), not just dropped — "recorded reason" is a concrete, queryable event, not a log line.

## Phase 1 — Provider Registry, Hosted HTTP Client, and the Grok CLI/Subscription Provider

### Requirements

- Add `llm.providers` to the instance config schema (`.e3d-corp/config.schema.json`, `lib/config.js`'s `validateInstanceConfig`), replacing `llm.baseUrlEnvVar`/`llm.modelEnvVar` and `roles.<name>.model`, per the Shared Constraints shapes above (`local`/`openai-compatible`/`grok-cli`). `validateInstanceConfig` detects the old flat shape specifically (presence of `llm.baseUrlEnvVar`/`modelEnvVar` or any `roles.<name>.model`) and names it explicitly in the error, pointing at `llm.providers` — not a generic "unknown field" message.
- `lib/llm/registry.js` (new): `resolveProvider(instanceConfig, providerName)` reads the named entry, resolves it per its `kind`, and returns `{ call, model }` — `call: ({ systemPrompt, userPrompt }) => Promise<string>` (the same shape `createLocalLlmClient` already returns, so every existing single-provider call site keeps working once it goes through the registry) and `model`: the resolved model string (or `"grok-cli-default"` for an unconfigured `grok-cli` model). Throws a clear error naming the provider and the specific missing env var/binary when resolution fails, never silently falls back.
- `lib/llm/openaiCompatibleClient.js` (new): the generic hosted HTTP client for a future `openai-compatible` provider — same request/response handling as today's `callLocalLlm`, plus an `Authorization: Bearer ${apiKey}` header, plus a `timeoutMs`-driven `AbortController`. `lib/llm/localClient.js` keeps its current behavior (no auth header) for `kind: "local"`, gaining only the timeout wrapper — `callLocalLlm`'s `fetch` has no timeout today; this closes that gap for every HTTP provider, not just new ones.
- `lib/llm/grokCliClient.js` (new): the `grok-cli` provider, a direct Node port of e3d-pilot's `lib/providers/grok-build` "analysis" mode — the mode is right for e3d-corp because these roles only ever need a completion, never file writes. Concatenate `systemPrompt` and `userPrompt` into one prompt file (matching how e3d-pilot's stage prompts are already file-based), then `child_process.spawn` the resolved `grok` binary with `--no-auto-update --cwd <repo root> --prompt-file <file> --output-format plain --no-memory --no-subagents --always-approve --sandbox read-only` (plus `--model <resolved>` when `modelEnvVar` is configured), capture stdout as the completion text, and enforce `timeoutMs` by killing the subprocess on expiry — the direct equivalent of `provider_run_with_timeout`. No `apiKeyEnvVar` — auth is whatever OAuth session `grok login --device-auth` already established on the machine; this provider only checks that the binary exists and lets `grok` itself fail loudly if that session is missing or expired.
- `e3d-corp providers status --instance <name>` (new CLI command, per Shared Constraints) — read-only, makes no completion calls; reports env-var presence for HTTP-kind providers and binary presence for `grok-cli`.
- Migrate `.e3d-corp/instance/futco/instance.json` (gitignored, real) and `examples/instance.example.json` from the flat `llm.baseUrlEnvVar`/`modelEnvVar`/`roles.<name>.model` shape to `llm.providers.local = { kind: "local", baseUrlEnvVar, modelEnvVar }` and `roles.<name>.provider: "local"` (unchanged value, new field shape). Add a `grok` entry (`{ kind: "grok-cli" }`, no other fields required) to the real futco instance config so it's available to reference from a role once Phase 2/3 land — this phase does not point any role at it yet.
- Document Grok concretely (new `docs/grok-provider.md`, structured like `../e3d-pilot/docs/grok-build.md`): installation and auth is exactly e3d-pilot's own `grok login --device-auth` step — if it's already done for e3d-pilot on this machine, e3d-corp's `grok-cli` provider uses the same session, nothing new to set up. Cover configuration (the `grok-cli` provider shape above), and what happens when the provider is unavailable (binary missing or session expired surfaces as a clear resolve-time/runtime error, flagged ahead of time by `providers status` where possible, never a silent fallback to local).

### Acceptance Criteria

- `config validate` against an instance config using `llm.providers.local` (no `grok` entry) behaves identically to today's flat-shape config for every existing role invocation — all Phase 1-10 tests from `docs/build-e3d-corp.md` continue to pass, with fixtures updated for the new config shape (behavioral assertions unchanged).
- A config still using the old flat `llm.baseUrlEnvVar`/`modelEnvVar` or `roles.<name>.model` shape fails `config validate` with an error naming those specific fields and pointing at `llm.providers`.
- `providers status` against a config with `grok-cli` configured and the `grok` binary absent from `PATH` reports it as not-ready, naming the missing binary, without attempting a call. Against a config with an unset `apiKeyEnvVar` for an `openai-compatible` entry, same behavior for the missing env var.
- Against a config with `llm.providers.grok = { kind: "grok-cli" }`, on a machine already authenticated via e3d-pilot's `grok login --device-auth`, `resolveProvider(config, "grok").call(...)` makes one real `grok` subprocess call and returns real model output, billed to the subscription — run this for real, once, by hand, the same one-time "real, not fixture" bar `docs/build-e3d-corp.md` holds Phase 3/4/7 to; this is not a repeatable suite check, and CI/automated test runs use a stubbed `call` exactly as every other provider's tests already do.
- A role config naming a provider not present in `llm.providers` fails `config validate` with an error naming the specific missing provider, not a generic schema error.
- A provider call that exceeds its `timeoutMs` is aborted (HTTP: `AbortController`; `grok-cli`: the child process is killed) and surfaces as a clear timeout error, not a hang.

## Phase 2 — Multi-Provider Fan-Out for `opportunity.prospect`

### Requirements

- `roles["opportunity.prospect"].provider` accepts `string | string[]`. `lib/roles/opportunityProspect.js`'s `runOpportunityProspect` keeps its evidence-gathering exactly as it works today — evidence is fetched **once**, before any provider is called, using the same `evidenceEvents.length === 0` check that exists now. Only after that shared evidence snapshot exists does the function resolve one client per named provider (via Phase 1's registry) and invoke all of them concurrently against that same evidence. This is a specific, load-bearing requirement: calling today's function once per provider independently would make each invocation see zero evidence and could re-run the same (potentially paid) research query once per provider.
- Each provider's response is validated exactly as today (`normalizeOpportunityCandidate`/`parseCandidateJson`) — a malformed response from one provider is dropped and recorded as a `role.provider.failed` event (Shared Constraints), and does not affect the others' candidates. If every provider in the list fails or returns invalid output, the whole call throws exactly as today's single-provider path does.
- `lib/opportunities/schema.js`'s Opportunity record gains `proposedBy: { role, provider, model }` (new field; Proposal already has the equivalent), populated from Phase 1's `resolveProvider(...).model`. `lib/opportunities/engine.js`'s `runOpportunityEngine` creates one full Opportunity (own `id`, own `proposedBy`) per surviving candidate — but every sibling **shares the triggering event's `correlationId`**, exactly as the single-candidate path does today (`candidate.correlationId = triggerEvent.correlationId`, set in `opportunityProspect.js`). Siblings are distinguished by `id` and `proposedBy`, not by forking the chain: `reconstructChain(correlationId)` is a bare correlationId lookup (`lib/events/chain.js`), so a fresh correlationId per candidate would silently sever it from its own triggering event and evidence — breaking `opportunity.prospect`'s own evidence lookup, `communicator.js`'s `deriveRecipient` (which walks the chain for a lead email), and `docs/build-e3d-corp.md`'s stated traceability guarantee. Do not give fanned-out candidates separate correlationIds.
- `runOpportunityEngine`'s return shape changes from `{ opportunity, createdEvent, scoredEvent }` to `{ opportunities: [...], createdEvents: [...], scoredEvents: [...] }` (plural, arrays — even for a single-provider role, which returns one-element arrays, so callers have one shape to handle). Update both call sites explicitly: `lib/web/server.js`'s lead-ingest handler and `runDiscoveryPass` (`lib/opportunities/engine.js`, currently destructuring `{ opportunity }`), plus `test/phase4.test.js`.

### Acceptance Criteria

- Against two stubbed LLM endpoints returning distinct fixture candidates, a 2-provider `opportunity.prospect` config produces two distinct, correctly-scored Opportunities from one trigger event, each with the correct `proposedBy.provider`/`model`, both sharing the trigger's `correlationId`, both `causationId`-linked to the same trigger, and both findable via `reconstructChain(triggerEvent.correlationId)` alongside the trigger and its evidence.
- Evidence is gathered exactly once (one `evidence.gathered` event, one research-adapter call) for a 2-provider run against a trigger with no prior evidence — not twice.
- One provider returning malformed JSON while the other returns a valid candidate produces exactly one Opportunity (from the valid provider) and one `role.provider.failed` event for the other — the malformed response never becomes a half-written Opportunity record, matching today's single-provider malformed-output behavior.
- Both configured providers failing produces the same error `runOpportunityEngine` raises today for its one provider failing, plus two `role.provider.failed` events — no new failure mode for the "everything failed" case.
- A single-provider (string) config produces the same Opportunity content as today, in the new one-element-array return shape, including the now-populated `proposedBy` field — regression-checked against `test/phase4.test.js`, updated for the new shape and field.
- A provider that exceeds its timeout is recorded as a `role.provider.failed` event with a timeout reason and does not block the other provider(s) in the list from completing.

## Phase 3 — Multi-Provider Fan-Out for `opportunity.communicator`

### Requirements

- Same provider-list mechanism as Phase 2, applied to `roles["opportunity.communicator"].provider` in `lib/roles/communicator.js`'s `runOpportunityCommunicator`/`buildPrompt`. Each provider drafts independently against the same opportunity/evidence chain (the chain is already fully formed by this point — Phase 2's evidence-sharing concern doesn't apply here); each surviving draft becomes its own `pending` `send-outreach` Proposal (authority level 2, unchanged), sharing the opportunity's `correlationId` exactly as a single-provider draft does today, with `proposedBy.provider`/`model` distinguishing them.
- Extend the `/proposals` web UI (and `proposals list`/`proposals show` CLI) so sibling drafts for the same opportunity are visibly grouped — a human reviewing them needs to see they're alternatives for the same outreach, not unrelated proposals.
- **The duplicate-outreach guard must be atomic and must run before a proposal is durably marked approved, not just before the action fires.** `lib/decisions/decide.js` appends `proposal.approved` to the append-only event log and then invokes the action executor in the same call for a level-2 proposal — the event log entry cannot be un-appended. If the guard only lived inside `sendOutreach.js` and ran after that append, a refused fire would leave the proposal permanently `approved` with no action ever executed and no clean status to represent that. Instead:
  1. `decideProposal` checks — before appending `proposal.approved` for a `send-outreach` type — whether an `outreach.sent` event already exists for the opportunity's `correlationId` (not the proposal's own `subject`, which differs per sibling proposal). If one exists, `decideProposal` refuses the whole approval with a clear "outreach already sent for this opportunity" error; nothing is appended.
  2. This check-then-decide sequence is wrapped in `lib/store/appendOnlyLog.js`'s `withFileLock` — the same lock `appendEvent` already uses to make its causationId-existence check atomic — so two concurrent approvals of sibling proposals can't both pass the check before either's `outreach.sent` is appended.
  3. `sendOutreach.js` keeps its own equivalent check as defense in depth (the action-execution function refusing independently of what called it, matching this codebase's existing "enforced at the call site, not just the UI" rule) — but the primary guard, and the one that keeps a rejected sibling from getting stuck in a confusing state, is the pre-approval check in step 1.
- No auto-rejection of un-fired siblings once one fires — they stay visible as `pending` so the audit trail shows what was drafted and what was chosen, not silently cleaned up. (They simply can never be approved after the fact, per the guard above.)

### Acceptance Criteria

- A 2-provider `opportunity.communicator` config against a `pursuing` opportunity produces two `pending` `send-outreach` Proposals, correctly `proposedBy`-attributed, both sharing the opportunity's `correlationId`, both visible and grouped in `/proposals` and the CLI.
- Approving and firing one sibling proposal succeeds exactly as today's single-provider path does (`outreach.sent` emitted, correct `causationId`/`correlationId`).
- Attempting to approve the other sibling afterward is refused at `decideProposal` itself, before any event is appended — the proposal remains `pending`, not stuck at `approved`, and no second `outreach.sent` event is ever created.
- Two sibling proposals approved concurrently (simulated in a test by racing two `decideProposal` calls) result in exactly one `outreach.sent` event and one successful approval; the other is refused.
- A single-provider (string) `opportunity.communicator` config behaves identically to today, including the now-enforced pre-approval guard protecting against any future double-approval, not just the multi-provider case.
